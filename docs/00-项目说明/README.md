## 文档说明

编写依据。本文档依据业务方提出的系统功能构思（组织架构、基础数据、门店、商品与价格、外勤、销售、库存、报表、权限、接口、日志，以及移动端四类场景）编写，同时参考了冰淇淋品类在菲律宾市场的作业特点，包括短保质期、强冷链、高频次小批量订货、现金与短账期赊销并存等。凡涉及当地税务、票据、劳动用工的具体要求，均以当地专业机构的意见为准，本文档只提出系统配置要求。

使用方式。文档采用“总体要求—核心流程—模块明细—非功能—数据”的结构。第2章确立的全局规则与状态体系是后续所有模块的前提，阅读模块章节前应先理解第2章；第3章按一级菜单逐一展开，每个模块均给出功能点编号、字段说明与业务规则，可直接作为开发任务拆解与测试用例编写的依据；第4章为移动端需求，需与第3章对照阅读，避免两端能力冲突。

变更管理。文档定稿后，任何功能范围、字段、状态或规则的调整，须由提出方填写变更说明，经产品负责人与业务负责人确认后更新版本号，并在下表登记。未登记的变更不进入开发排期，避免实现与文档脱节。

## 1  引言

<a id="section-1-1"></a>

### 1.1  项目背景

<a id="section-1-1-1"></a>

#### 1.1.1  业务现状

蒙牛在菲律宾的冰淇淋业务采用“总部—事业部—大区—经销商”四级渠道体系运作。总部负责品牌、产品与价格策略，冰淇淋事业部承担品类经营与渠道政策制定，四个大区（按菲律宾地理分布划分，示例为吕宋北大区、马尼拉大区、米沙鄢大区、棉兰老大区，实际命名以组织公告为准）负责区域内经销商的管理与督导，四十余家经销商承担对终端门店的实际销售、配送与收款。

经销商的销售对象以社区型杂货店（Sari-sari Store）为主，同时覆盖现代渠道超市与便利店、餐饮与甜品店、加油站便利店、学校与景区等点位。业务特征表现为单店面积小、单次订货量低、拜访频次高、现金交易与短账期赊销并存，且冰淇淋属于短保质期、强冷链品类，对到货时效、陈列位置与库存周转极其敏感。

一线销售存在两种基本作业模式。访销模式下，业务员按线路逐店拜访，现场采集订单，次日由配送员按单送货、当面签收并收款；车销模式下，业务员自行驾驶装有商品的车辆沿线巡回，现场开单、现场卸货、现场收款，日终回仓交款。两种模式共用同一批门店与商品，但订单来源、库存归属、收款时点和考核口径不同。

<a id="section-1-1-2"></a>

#### 1.1.2  当前存在的主要问题

在缺少统一系统支撑的条件下，总部与经销商之间的管理依赖报表、电话与即时通信工具，一线作业依赖纸质订单与手工台账。经梳理，主要问题集中在六个方面，见表1。

**表1  现状问题与业务影响**

| 序号 | 问题类别 | 具体表现 | 对业务的影响 |
| --- | --- | --- | --- |
| 1 | 组织与人员台账分散 | 总部、事业部、大区、经销商各自维护人员名单，经销商业务员入离职后总部无法及时感知；同一名业务员可能同时服务多个门店但无人知晓 | 督导对象不清，拜访计划无法按人下发，人员变动后线路失效 |
| 2 | 门店档案不统一 | 门店名称、地址、联系人、坐标由业务员自行记录，重复建档与“同名不同店”并存；门店分类口径不一致 | 拜访覆盖率无法统计，配送地址错误，重复投入人力 |
| 3 | 拜访过程不可见 | 是否到店、停留多久、做了什么动作、拍了什么照片，均无系统留痕；代签到、集中补录时有发生 | 外勤真实性无法验证，陈列与铺货执行不到位却无法追责 |
| 4 | 订单与库存脱节 | 订单在纸质单据或聊天工具中流转，库存靠仓管记忆与手工台账，超卖、缺货、重复发货难以避免 | 订单履约率低，退货与客诉增加，库存账实不符 |
| 5 | 收款与对账靠手工 | 现金、支票、转账、电子钱包多种收款方式混用，业务员日终交款凭记忆汇总，差异靠事后追查 | 应收账款不清，资金风险高，业务员与财务长期存在对账争议 |
| 6 | 缺少统一数据口径 | 销量、销额、拜访数、活跃门店数在各层级各算一套，报表口径与统计周期不一致 | 管理层无法基于同一套数据做决策，考核结果缺乏公信力 |

<a id="section-1-1-3"></a>

#### 1.1.3  建设必要性

上述问题的共同根源在于业务过程没有沉淀为结构化数据：组织、门店、商品等主数据缺乏唯一来源，订单、库存、收款三类核心单据没有形成闭环，外勤行为没有可验证的记录。仅靠制度约束与人工检查，管理成本会随经销商数量与门店数量同步上升，且无法支撑总部对四个大区的横向比较。

建设一套覆盖“组织与主数据—外勤过程—订单履约—库存—收款对账—报表”的经销商运营系统，可以把一线作业动作转化为可追溯的数据记录，把订单、库存、资金三条链路打通，使总部、事业部、大区、经销商在同一套口径下管理。系统同时需要适应菲律宾的网络条件与作业习惯，移动端必须具备离线可用能力，避免因信号不稳定导致一线停工。

### 1.2  文档目标

<a id="section-1-2-1"></a>

#### 1.2.1  文档用途

本文档是蒙牛菲律宾冰淇淋经销商运营系统的产品需求文档（PRD），用于明确一期建设的功能范围、页面与字段、按钮行为、单据状态、业务规则、接口要求以及非功能与数据要求。文档作为需求评审、开发实现、测试用例设计、上线验收与一线培训的共同基线，任何范围变更须以本文档的版本修订记录为依据。

本文档描述“系统应当做什么”，不描述具体技术实现方案（如框架选型、数据库表结构、部署拓扑）。界面原型、交互细节与视觉规范在后续《交互设计说明》中细化，但不得与本文件规定的字段、状态与规则冲突。

#### 1.2.3  文档范围

本期建设范围包括：PC端十一个一级功能模块（组织架构、基础数据、门店管理、商品与价格、外勤管理、销售管理、库存管理、报表管理、权限管理、三方系统接口、操作日志），移动端四类核心场景（我的首页、拜访、我的门店、设置与离线），以及与总部系统的订单接口。

### 1.3  术语定义

为避免各层级对同一名词理解不一致，本文档统一使用下表术语。文中出现的英文缩写与代码，均以本表定义为准。

**表3  术语定义**

| 术语 | 英文 / 代码 | 定义与说明 |
| --- | --- | --- |
| 业务单元 | Business Unit / BU | 组织架构中的管理实体，可独立配置人员、仓库与数据权限。本系统中总部、事业部、大区、经销商均为业务单元，经销商为叶子节点 |
| 事业部 | Business Division | 按品类或业务线划分的一级经营单元，本项目为冰淇淋事业部，下辖四个大区 |
| 大区 | Region | 按地理范围划分的管理单元，负责辖区内经销商的督导与考核 |
| 经销商 | Distributor | 独立承担仓储、配送、销售与收款的合作伙伴，系统中作为一个业务单元，拥有独立仓库、价目表与人员 |
| 门店 / 客户 | Outlet / Customer | 经销商的下级销售对象，是订单、拜访、收款的最小业务单元。本文档中“门店”与“客户”同义，界面统一称“客户”，业务口语称“门店” |
| 访销 | Presales | 业务员上门采集订单、次日配送的作业模式，订单与配送分离 |
| 车销 | Van Sales | 业务员驾车带货现场销售、现场收款、日终回仓的作业模式 |
| 外勤动作 | Field Activity | 一次拜访中需要完成的标准化动作，如签到、拍门头照、铺货上报、开单等，是外勤类型的最小组成单位 |
| 外勤类型 | Activity Type | 若干外勤动作的组合模板，用于区分不同性质的拜访，如“标准访销拜访”“新店开发”“陈列检查” |
| 外勤规则 | Activity Rule | 规定某类外勤类型适用于哪些人、哪些门店、在什么时间与地理范围内执行，以及必须满足的约束条件 |
| 线路 | Route / Journey Plan | 由若干门店按顺序组成的拜访路径，绑定业务员与拜访周期，是生成每日拜访计划的依据 |
| SKU | Stock Keeping Unit | 最小库存与销售单元。冰淇淋以“箱”为库存主单位，以“支/袋”为最小销售单位，两者按固定换算率转换 |
| 价目表 | Price List | 按渠道、客户等级、生效期间定义的商品销售价格集合，支持阶梯价与最低售价控制 |
| 铺货 | Distribution / Coverage | 门店在售本品牌商品的状态，分为必铺品项、选铺品项与未铺货，是陈列与拜访检查的核心指标 |
| 销售订单 | SO / Sales Order | 门店向经销商提出的购买请求，经审核后作为发货依据 |
| 发货单 | DN / Delivery Note | 按订单生成的配送指令，承载配送明细、配送状态与签收结果 |
| 销售出库 | Sales Outbound | 仓库按发货单实际出库的动作，触发库存扣减与成本结转 |
| 收款单 | Receipt | 登记一笔实际收到的款项，支持现金、支票、银行转账、电子钱包（GCash、Maya）等结算方式 |
| 应收 / 欠款 | AR / Accounts Receivable | 订单签收后形成的、尚未收回的货款余额，按门店维度归集 |
| 账期 | Credit Term | 允许门店在签收后延后付款的天数，常见为 7 天、15 天、30 天，按客户档案约定 |
| 信用额度 | Credit Limit | 允许单个门店未结清应收的最大金额，超限时按规则拦截或转审批 |
| 对账 | Reconciliation | 业务员当日经手的订单、收款与实交款项之间的核对，以及对门店应收余额的确认 |
| 交款 | Cash Handover | 业务员将代收现金或票据移交财务的动作，系统以交款单记录并核销对应收款单 |
| 批次 / 效期 | Batch / Expiry Date | 同一生产批次的商品及其保质期截止日期，冰淇淋按批次管理，出库遵循先进先出与临期预警 |
| 车仓 | Van Warehouse | 挂在车辆上的移动虚拟仓库，用于管理车销在车商品，独立于经销商实体仓 |
| 离线模式 | Offline Mode | 移动端在无网络或弱网络下仍可查询计划、开单、登记收款，联网后自动或手动上传 |
| 幂等 | Idempotency | 同一请求重复提交时结果一致，不产生重复单据。移动端重传与接口重试均依赖幂等键实现 |
| 增值税 | VAT | 菲律宾现行增值税，标准税率 12%。系统按含税/不含税两种价格口径配置，具体适用以当地税务顾问确认为准 |
